# Architecture Blueprint: The Pterodactyl-Mazzoli Elaborator

## 1. Core Philosophy
The `hwml-elab` crate acts as the bridge between the untyped Surface AST and the mathematically rigid Core AST. It operates on three fundamental principles:
1. **LCF-Style Unforgeability (Pterodactyl):** The Elaborator itself is "untrusted" and cannot manually construct Core `Syntax` or `Ty` nodes. It must use a trusted `Kernel` API to build terms.
2. **Deferred Constraint Solving (Mazzoli):** Difficult problems (like unification or universe bounds) are not solved eagerly. They are emitted as constraints to a global `SolverState` and resolved asynchronously.
3. **Large-by-Default Universes (Sterling):** The surface language has no universe levels. Polymorphism is handled by injecting metavariables and tracking upper/lower bounds, defaulting to the lowest possible level at the end of compilation.

---

## 2. The Trusted Kernel (`kernel/`)

To guarantee mathematical soundness, the rules of our type theory are isolated in a trusted module. 

### A. The `Trust<T>` Wrapper
A zero-cost abstraction that proves a Core term was generated by a valid typing rule.
```rust
pub struct Trust<T>(T);

impl<T> Trust<T> {
    // PRIVATE: Only the Kernel module can construct this!
    pub(crate) fn new(value: T) -> Self { Self(value) }
    
    // PUBLIC: Anyone can read the inner value.
    pub fn into_inner(self) -> T { self.0 }
}
```

### B. The Bidirectional Traits
Typing rules are modeled as structs that implement push (`check`) or pull (`synth`) traits.
```rust
#[async_trait]
pub trait CheckRule<'db> {
    async fn check(&self, elab: &mut Elaborator<'db>, expected: Rc<Ty<'db>>) 
        -> Result<Trust<Rc<Syntax<'db>>>, ElabError>;
}

#[async_trait]
pub trait SynthRule<'db> {
    async fn synth(&self, elab: &mut Elaborator<'db>) 
        -> Result<Trust<(Rc<Syntax<'db>>, Rc<Ty<'db>>)>, ElabError>;
}
```
*Example:* `LambdaIntro` is a struct implementing `CheckRule`. Its `.check()` method forces the expected type to WHNF, extends the environment with a fresh variable, recursively checks the lambda's body, and returns `Trust(Syntax::Lam(...))`.

## 3. State Management (`state.rs`)

Elaboration requires managing both a branching local scope and a monotonically growing global constraint graph.

### A. Local Context (`ElabEnv`)
Tracks the current variables in scope as the Elaborator goes under binders.
* **`names: im::Vector<String>`**: User-defined names for scope resolution.
* **`types: im::Vector<Rc<Ty>>`**: Semantic types for synthesis.
* **`values: im::Vector<Rc<Value>>`**: Runtime values (usually fresh neutrals) for substitution.
* *Key detail:* Uses `im::Vector` to provide `O(1)` cloning when exploring multiple branches (e.g., in `Case` expressions).

### B. Global Constraint Graph (`SolverState`)
Tracks unknowns and defers complex checks. Sits behind an `Rc<RefCell<>>` so rules can emit constraints without needing mutable ownership of the Elaborator.
* **`meta_types: HashMap<MetaId, Rc<Ty>>`**: Records the expected type of every minted `?meta`.
* **`solutions: HashMap<MetaId, Option<Rc<Value>>>`**: Holds the solved instantiation of a `?meta`, or `None`.
* **`constraints: Vec<Constraint>`**: The backlog of deferred mathematical proofs.

### C. The `Constraint` Enum
The actual deferred work the solver must complete.
```rust
pub enum Constraint<'db> {
    /// Prove that Type A is definitionally equal to Type B
    Unify(Rc<Ty<'db>>, Rc<Ty<'db>>),
    
    /// Prove that LHS is a universe level less than or equal to RHS
    LevelLeq(Rc<Value<'db>>, Rc<Value<'db>>), 
}
```

## 4. Universe Polymorphism & Constraint Solving

We achieve "Fuss-Free" universe polymorphism without changing the Core AST to support level algebra.

### A. The Syntax Meta Trick
When the Elaborator sees the `Type` keyword in the surface language, it does **not** create a special level variable. It mints a standard Core `Syntax::Metavariable` whose expected type is `Ty::UniverseType`.

### B. Bounding Constraints (`LevelLeq`)
Instead of solving exact algebraic equations like `max(?u, ?v)`, the constraint solver simply tracks the **lower bound** and **upper bound** for every `UniverseType` metavariable. 
* If a function expects `Type 0` but is given `Type ?u`, the Elaborator emits `LevelLeq(?u, 0)`. The solver updates `?u`'s upper bound to `0`.

### C. Zonking (The Defaulting Pass)
At the end of elaborating a file, some universe metavariables will remain unsolved (e.g., an unused polymorphic identity function). 
1.  The Zonker iterates over `SolverState::solutions`.
2.  If a meta is unsolved, it checks its expected type.
3.  If it is a `Ty::UniverseType`, it **permanently instantiates it to its lowest valid bound** (usually `0`).
4.  This generates a 100% concrete Core AST (`UniverseCode(0)`) perfectly suited for the `LiftCode` modular shunt during multi-file linking.

## 5. The Hardware Firewall

Because we use **Tarski-style Typecodes**, the Elaborator must use the `Ty::El` bridge to convert computing values into classifying types. This provides perfect domain separation between hardware and software.

* **Software Universe Rule:** Synthesizes `Syntax::UniverseCode` and returns `Ty::UniverseType`.
* **Hardware Signal Rule:** Synthesizes `Syntax::BitCode` and returns `Ty::SignalUniverseType`.

If a user tries to apply a software lambda to a hardware wire, the fallback `check` rule will emit `Constraint::Unify(Ty::SignalUniverseType, Ty::UniverseType)`. The constraint solver will see the distinct enum tags, fail immediately, and report a clean domain-mismatch error without the Core evaluator ever touching it.
